## 🔍 更正：Level B 早已实现（本轮初稿写错，已核实）
初稿曾写"Level B 未实现"，**与事实不符**。核实结果：
- `ContinueSessionService.continue()`（`runtime-services.ts:89/113`）：只要 `session.externalSessionId` 存在，就走 `buildResumeInfo()` + `resume()`，命令为 `codex exec resume <uuid> -`。
- 已有测试覆盖：`runtime-api.test.ts:347`「resumes the bound Codex session with an incremental context prompt」断言 `launch.operation === "resume"`、`externalSessionId` 正确、`args` 含 `["resume", uuid]`；`codex-adapter.test.ts:25` 断言 resume args 为 `["exec","resume","codex-session","-"]`。
- 首次 launch 后会自动把 Codex 会话绑到 Session 行（`runtime-api.test.ts:221`）。

**但顺着这条线发现本轮新功能的一个真缺口并已修**：`DesktopSyncService.bind()` 只把 externalSessionId 写进 `session_sync_state`，**没有写回 `sessions.external_session_id`** —— 而 `continue` 正是读该字段来决定 launch 还是 resume。结果是：用 Desktop 同步面板绑定的会话点「继续」时，仍会开一个全新线程，而不是续跑刚同步的那个 UUID，"同 UUID 续跑"的能力标记名不副实。
- 修法：`DesktopSyncService` 新增可选端口 `bindExternalSession`（闭包），bootstrap 接到 `SqliteRuntimeRepository.bindExternalSession()`；会话行未绑定时写入，已绑到**另一个** external id 时抛 `CONFLICT`（HTTP 409，原绑定不动）。
- 测试：绑定后断言 `sessions.getByIdOrThrow(id).externalSessionId` 已写入；重绑不同 id 断言 409 且原绑定不变。测试 server 补了与生产一致的错误码映射（CONFLICT→409），否则 ContextOsError 会落到 500。
